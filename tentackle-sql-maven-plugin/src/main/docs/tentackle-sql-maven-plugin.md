## The Tentackle SQL Maven Plugin

The `tentackle-sql-maven-plugin` turns the Tentackle [entity model](../../../../tentackle-model/src/main/docs/model-definition.md)
into database DDL. Where the [`tentackle-maven-plugin`](../../../../tentackle-maven-plugin/src/main/docs/tentackle-maven-plugin.md)
generates the Java- and service metadata of an application, this plugin is responsible for everything
that touches the database schema:

- generating a `CREATE TABLE` script for a fresh database,
- generating an incremental migration script by comparing the model against the metadata of an
  existing database,
- validating that a database is still in sync with the model,
- running arbitrary SQL scripts against the configured backend(s), and
- rendering the model as a set of cross-linked HTML pages for browsing.

All goals derive the schema from the same model and emit backend-specific SQL through Tentackle's
`org.tentackle.sql.Backend` abstraction, so the very same model can be materialized for PostgreSQL,
MySQL/MariaDB, Oracle, H2, and the other supported backends without changing a single model file.

The goals share the prefix `tentackle-sql`, so they can be invoked directly from the command line,
e.g. `mvn tentackle-sql:create`.

### Prerequisites

The plugin requires the same JDK and Maven versions as the rest of the framework
(JDK >= 25, Maven >= 3.9.10, Maven 4 is supported as well). The `migrate`, `validate`, `run` and `reveng` goals connect to a live
database and therefore need a reachable backend and the matching JDBC driver on the plugin's
classpath (add it to the plugin's `<dependencies>`). For `reveng` that backend is typically the
*existing* database being reverse-engineered, not necessarily the application's own.

### Where the Model Comes From

None of the goals parse Java sources directly. They read the *model* — the entity definitions that the
wurbelizer extracts from the PDO interfaces during code generation and writes to
`${project.build.directory}/wurbel/model` (one file per entity). This is the default value of the
`modelDir` parameter, so in a normal Tentackle build the SQL plugin just picks up what the wurbelizer
already produced earlier in the same build. You can point it elsewhere with `modelDir` or override the
selection entirely with explicit `filesets`.

The one exception is `reveng` (see [below](#the-reveng-goal)): it goes the other way, reading an
*existing* database's live schema and writing model source text for `tentackle-wizard:pdo` to
consume — it never reads `modelDir`/`filesets` and has nothing to do with the model of the project
it runs in.

Because all goals are aggregators (they operate on the whole reactor at once), they are typically run
on the root project rather than per module.

### Overview of Goals

| Goal       | Aggregator | Connects to DB | Purpose                                                                                                        |
|------------|------------|----------------|----------------------------------------------------------------------------------------------------------------|
| `create`   | yes        | no             | Generate a `CREATE TABLE` script (plus indexes, foreign keys, schemas, sequences) for the whole model.         |
| `migrate`  | yes        | yes            | Compare the model against the live database metadata and generate an incremental migration script.             |
| `validate` | yes        | yes            | Like `migrate` with `validate=true`: fail the build if the database differs from the model.                    |
| `run`      | yes        | yes            | Execute an arbitrary SQL script against the configured backend(s).                                             |
| `document` | yes        | no             | Render the model as cross-linked, backend-specific HTML or Markdown pages, one per entity, plus an index page. |
| `reveng`   | yes        | yes            | The reverse direction: turn tables of an *existing* database into model source for `tentackle-wizard:pdo`.     |
| `help`     | —          | no             | Print plugin usage information (generated by the maven-plugin-plugin).                                         |

The generated scripts are written per backend to `${project.build.directory}/sql/<backend-name>/`,
e.g. `target/sql/postgres/createmodel.sql`. `document` follows the same per-backend layout, writing to
`${project.build.directory}/model-doc/<backend-name>/`.

### Common Configuration

Like all Tentackle mojos, the goals inherit the common parameters `verbosity`, `skip`, `charset`,
`jdkToolchain` and `minLogLevel` (see the [`tentackle-maven-plugin` docs](../../../../tentackle-maven-plugin/src/main/docs/tentackle-maven-plugin.md#common-configuration)).
On top of that, `AbstractSqlMojo` adds the parameters shared by all goals except `reveng`, which is
configured separately (see [below](#the-reveng-goal)).

- `sqlDir` (`tentackle.sqlDir`): the base directory of the generated scripts, one sub-directory per
  backend. Defaults to `${project.build.directory}/sql`.
- `generateHeaderComment` (default `true`): start each generated script with a comment naming the
  model location, the creation time, the user and host, and the backend.

All goals are thread-safe. The model, however, is held in a JVM-wide singleton, so in a parallel build
(`mvn -T …`) concurrent executions are serialized, except for `reveng`; see
[Parallel builds](../../../../tentackle-maven-support/src/main/docs/tentackle-maven-support.md#parallel-builds).

#### Model selection

- `modelDir` (`tentackle.modelDir`): directory holding the model files. Defaults to
  `${project.build.directory}/wurbel/model`. Ignored if `filesets` is given.
- `filesets`: explicit file sets to process instead of `modelDir`.
- `modelName` (`tentackle.modelName`): the model to use, for the rare case that a project defines more
  than one. Defaults to the standard model.
- `modelDefaults` (`tentackle.modelDefaults`): model defaults applied to every entity (same syntax as
  the `[defaults ...]` block in a model file).
- `entityAliases` (`tentackle.entityAliases`): entity alias definitions.
- `mapSchemas` (`tentackle.mapSchemas`): map schema-qualified table names to flat table names, for
  backends that do not support schemas (Oracle, MySQL, MariaDB, Firebird, Informix). Must match the `mapSchema`
  wurblet property that configures the runtime side — see
  [Table Names](../../../../tentackle-session/src/main/docs/table-names.md).

#### Backend selection

The set of backends to generate SQL for can be specified in three ways, which may be combined. Later
definitions override earlier ones for the same backend name:

1. **By name** via `backendNames` (`tentackle.backendNames`) — a comma-separated list of backend
   names. The special values `all` (all non-deprecated backends), `none` and `deprecated` are
   recognized. This is the usual choice for the `create` and `document` goals, which do not need a
   connection.
2. **From property files** via `backendProperties` — file sets of `EncryptedProperties` files that
   describe a backend including its JDBC URL and credentials. If no `<directory>` is given, the
   project's resource directories are scanned. These backends are *connectable*.
3. **Inline in the pom** via `backends` — a list of `<backend>` elements (see below). Also
   connectable.

A connectable backend is required for `migrate`, `validate` and `run`; `create` and `document` work
with name-only backends because they never touch a database.

```xml
<backends>
  <backend>
    <url>jdbc:postgresql://localhost/muz</url>
    <user>muz</user>
    <password>secret</password>
    <schemaNames>muz, tx</schemaNames>   <!-- or a <schemas> list of <schema> elements -->
  </backend>
</backends>
```

Instead of an inline `<user>`/`<password>` you can reference a `<serverId>` from `settings.xml`; the
plugin then reads the (optionally encrypted) credentials from the maven settings. The `<minVersion>`
element is used for migration-hint version filtering (see below).

#### Name checks

- `checkModelNames` (default `true`): check the entity, attribute, relation and index names of the
  model with the
  [`NameVerifier`](../../../../tentackle-model/src/main/docs/tentackle-model.md) (application naming
  conventions on top of the backend rules). Turn it off to load
  legacy models whose names don't follow the rules.
- `checkReservedTables` (default `true`): assert that no model table reuses a name reserved by the
  Tentackle framework.
- `checkBackendSpecificNames` (default `true`): assert that column, schema, table, and index names do
  not collide with reserved words of the configured backends.
- `alienTables`: a list of regular expressions matching tables that exist in the database but do not
  belong to the model (without schema prefix). They are excluded from the "unexpected tables"
  reporting and must not be claimed by a model entity.

#### Diagnostics and dumps

These parameters help inspect what the plugin understood from the model — useful for debugging and
for packaging a model so downstream projects can build on it:

- `dumpDir`: dump every parsed entity (plus `_aliases_.txt`, `_tables_.txt`, `_classid_.txt` index
  files). The formatting is controlled by:
    - `dumpCompact` (default `false`): print only the configuration keywords that are actually
      required, instead of all of them for proofreading;
    - `dumpAsComment` (default `true`): dump the entities as comment blocks;
    - `dumpVariables` (default `true`): include the model variables;
    - `dumpColumnGap` (default `2`): the minimum number of spaces between the columns of the attribute
      section;
    - `dumpAnnotationsAsOptions`: comma-separated annotations to print as attribute options, e.g.
      `@NotNull|, @NotZero`. A trailing `|` matches only annotations without parameters; `@*` matches
      all annotations.
- `dumpModelSource`: dump the original model source instead of the parsed entity.
- `dumpModelIndex`: also write an index file listing the dumped files — combined with
  `dumpModelSource` this produces a `META-INF/MODEL-INDEX.LIST` so the model can be loaded from a jar
  (see `prependModelFromClassPath` / `loadModelFromClassPath`).
- `bundleDir`: write `*.properties` bundles containing the attribute- and relation comments, ready to
  copy into the project for auto table configuration or default editors.

### The `create` Goal

Generates a script that creates the whole schema from scratch. For every table-providing entity it
emits, in order: the `CREATE SCHEMA` (unless `mapSchemas` or `createSchemas=false`), the
`CREATE TABLE`, its indexes, and finally the foreign-key constraints for the generated entities.

```bash
mvn tentackle-sql:create -Dtentackle.backendNames=postgres
```

The default output file is `createmodel.sql` (parameter `sqlFileName`, property `tentackle.createSqlFile`). Important parameters:

- `createSchemas` (default `true`): emit `CREATE SCHEMA` statements for schema-qualified tables. If a
  backend does not support schemas, set `mapSchemas` instead.
- `sequences`: a list of `<sequence>` elements (`name`, `comment`, `start`, `increment`) to create.
  Backends that do not support sequences get a commented-out note instead.
- `prependFilesets` / `appendFilesets`: file sets whose content is copied verbatim to the beginning
  resp. end of the generated script (e.g., for grants or seed data).
- `prependModelFromClassPath` / `appendModelFromClassPath`: also generate the tables for a model found
  on the classpath, e.g., the Tentackle framework's own tables. Requires the dependency to ship its
  model resources (built with `dumpModelSource` + `dumpModelIndex`).

### The `migrate` Goal

Connects to each connectable backend, reads its metadata via JDBC, compares it table by table against
the model, and generates the SQL needed to bring the database in line: adding/altering/dropping columns
and indexes, renaming columns whose data should be preserved, adjusting foreign keys, and renaming or
dropping tables where migration hints say so. If nothing differs, the script just records that no
migration is necessary.

#### How columns are matched

The migrator preserves data wherever it can. Columns that exist under the same name are altered in
place. For the rest — attributes the model added and columns the database still has — it looks for
pairs and generates a `RENAME` (or a combined rename and type change) instead of a drop plus an add:

1. an **unambiguous match by SQL type**: exactly one disappeared column has the type of the added
   attribute;
2. otherwise the **best match by syllable distance** among the candidates of the same type, starting
   with the longest names, which is why bulk renames such as `x_position → position_x`,
   `y_position → position_y` and `z_position → position_z` are usually paired correctly in one pass.

Wherever the migrator guesses, it writes the alternative `ADD` and `DROP` statements into the script as
comments, so a wrong guess can be corrected instead of silently applied. Only columns left without a
counterpart become a real `DROP` or `ADD`. Type changes a backend cannot perform in place are likewise
emitted as a comment rather than as a statement that would fail or lose data.

Table renames, by contrast, are never guessed — they need a `rename` hint.

```bash
mvn tentackle-sql:migrate
```

The goal **generates, it does not apply**: the script is written to
`${project.build.directory}/sql/<backend>/migratemodel.sql`, one per backend, and executing it is a
separate step. The intended lifecycle is to review the generated script, **commit it to the
repository** as a versioned migration, and let a migration tool such as
[Flyway](https://www.red-gate.com/products/flyway/) or Liquibase apply it to the databases it manages;
`tentackle-sql:run` is for trying it out locally, not for rolling it out. Note also that a necessary
migration is only a *warning* — the build stays green unless `validate` is set.

The default output file is `migratemodel.sql` (parameter `sqlFileName`, property `tentackle.migrateSqlFile`). Important parameters:

- `validate`: fail the build if any migration would be required (see the `validate` goal).
- `failOnUnexpectedTables` (default `false`): fail if the database contains user tables that are
  neither in the model nor declared as `alienTables`. When `false`, such tables are only listed as a
  comment with the suggestion to add them to `<alienTables>` or remove them.
- `loadModelFromClassPath` (`tentackle.loadModelFromClassPath`): migrate the model found on the classpath instead of the local model files
  (e.g., to migrate only the framework's tables). When set, the model files in the file sets are
  ignored; usually combined with `checkReservedTables=false`.
- `useDropIfExists`: use `DROP ... IF EXISTS` for dropping indexes, constraints, and columns where the
  backend supports it (a warning is logged otherwise).
- `split`: write one file per migrated table into numbered sub-folders instead of a single script —
  handy when the migrations are post-processed by shell scripts. `before all`/`after all` and the
  unconditional `always before`/`always after` hints get their own folders (`0…` and the highest
  number).
- `asTemplate` (`tentackle.migrateSqlAsTemplate`): treat the generated migration as a FreeMarker
  template. For each entity a boolean template variable `<entity-name>` is set (`TRUE` if it needs
  migration), so the final SQL can be tailored per entity.

#### Migration hints

The automatic migrator handles structural changes that can be derived mechanically — including column
renames, see above — but some changes need human guidance: renaming or dropping a *table*, converting
the data when a column changes its type (a string becoming a number, say), correcting a rename the
migrator guessed wrong, ordering migrations that depend on each other, choosing between alternative
automatic migrations, or injecting handwritten SQL. This is what *migration hints* are for.

Hints are plain text files supplied per backend via the `<migrationHints>` file sets inside a
`<backend>`. Each file is a sequence of sections; a section starts at the beginning of a line with a
keyword immediately followed by a colon and extends until the next keyword:

```
-- rename the customer table and one of its columns, then add hand-written SQL
rename kunde: customer
rename customer#kdnr: customer_no

before customer:
ALTER TABLE customer ADD COLUMN migrated_at timestamp;

depend invoice: customer
```

Recognized keywords:

| Keyword                            | Effect                                                                                           |
|------------------------------------|--------------------------------------------------------------------------------------------------|
| `always before` / `always after`   | SQL emitted unconditionally before/after everything else.                                        |
| `before all` / `after all`         | SQL emitted before/after everything else, only if something changed.                             |
| `before <table>` / `after <table>` | SQL emitted before/after the migration of that table (if changed).                               |
| `migrate <table>`                  | Hand-written SQL that *replaces* the automatic migration of that table (if changed).             |
| `migrate <table>#<col>[/<newcol>]` | Hand-written SQL for migrating a specific column (if changed).                                   |
| `rename <table>: <newtable>`       | Rename a table (same schema) when the old name exists in the DB and the new one is in the model. |
| `rename <table>#<col>: <newcol>`   | Rename a column under the same condition.                                                        |
| `drop <table>: <comment>`          | Generate a `DROP TABLE` for a table that exists but is no longer in the model.                   |
| `hint <table>: <regex>`            | Select one of the alternative automatic migrations the table migrator commented out.             |
| `depend <table>: t1, t2, …`        | Delay the migration of `<table>` until the listed tables are migrated.                           |
| `--`                               | A comment describing the hint; not copied into the generated SQL.                                |

Multiple sections for the same table/keyword are concatenated. Custom validators discovered via
`CustomMigrationValidator` are run against each generated migration and can fail the build.

#### Version filtering of hints

Hint files can be organized in version-named sub-directories so that only the hints newer than the
database's current version are applied. A backend's `<minVersion>` provides that current version and
may be:

1. a fixed version string such as `3.1.0`,
2. an SQL `SELECT` returning the version from the database, or
3. the fully-qualified class name of a `DatabaseVersionLoader` implementation (which must be on the
   plugin classpath).

The default `SemanticVersionFileFilter` interprets the hint directory name as a semantic version
(`major.minor.hotfix`, dots or underscores, optional `-SNAPSHOT`/`-M1` suffix) and applies the hint
only if its version is greater than the database version. Directories whose name does not start with a
digit are treated as permanent (always applied). The filter is pluggable via the `VersionFileFilter`
service.

### The `validate` Goal

A thin wrapper around `migrate` that forces `validate=true`: it generates the migration script as
usual but fails the build (`database meta data differs from object model`) as soon as any migration
would be necessary. Use it in CI to guarantee that a deployed database matches the committed model.

```bash
mvn tentackle-sql:validate
```

It accepts the same parameters as `migrate`.

### The `run` Goal

Executes a single SQL script against every configured connectable backend, using the backend's script
runner. It inherits the same backend configuration as `migrate`, which is convenient because the
target database is usually the same.

> **A development tool.** `run` is meant for the database on a developer's machine and for the test
> database of a build — trying out a generated migration, fixing up local data, looking at what is
> stored. It has no notion of which scripts a database has already seen, no versioning, no checksums
> and no rollback. **Regular migrations belong to a migration tool such as
> [Flyway](https://www.red-gate.com/products/flyway/) or Liquibase**, running the migration scripts
> that `migrate` generated and that you committed to the repository. That is what makes a migration
> reproducible across staging and production, and auditable afterwards.

```bash
mvn tentackle-sql:run -Dscript=src/sql/myscript.sql
```

- `script` (`script`, required): the SQL file to execute.

Every statement's outcome is logged: result sets as an aligned table with column headers, other
statements as their update count. The script is split on the backend's statement separator (`;`), and
`--` line comments and `/* … */` block comments are stripped before anything is sent to the database.

Two properties of the goal are easy to miss. It executes the script against **every** configured
connectable backend, one after another — a project configuring PostgreSQL and H2 runs it twice. And it
runs **without a transaction**: the connection is in autocommit mode, so a script that fails halfway
leaves the statements before the failure committed and fails the build.

### The `document` Goal

Renders the model as a set of static HTML or Markdown pages under `docDir`, nested one directory per
backend (`docDir/<backend-name>/`, same layout convention as `create`'s `sqlDir/<backend-name>/`): one
page per entity plus an `index.html` (or `index.md`). Each entity page shows the same relationship information as the
[`ModelComment`](../../../../tentackle-wurblets/src/main/docs/wurblets.md#the-wurblets) wurblet's
Javadoc comment block — referencing entities, composite/component structure, outgoing references, deep
references, composite membership and inheritance — except that every entity name mentioned is a
hyperlink to that entity's own page, so the whole model can be browsed by clicking through it instead of
manually finding the next file.

The index page has two sections: **Aggregates** lists each root entity that has components, with its
component tree (root entities without components are not aggregates in any useful sense and are left
out), and **All Entities** lists every entity with its comment. As in the `ModelComment` wurblet, an
N:M link component is followed by the entity on the opposite side, e.g.
`User2Group [N:M] to UserGroup as userGroups`.

It also shows two attribute tables: **Attributes**, the entity's user-declared attributes, and
**Framework Attributes**, the attributes added implicitly by the framework — `id`/`serial` on every
entity, plus `classId`, `tableSerial`, `rootId`/`rootClassId` and the tokenlock/`normText` attributes
where the corresponding entity option is set (see
[Root Columns](../../../../tentackle-pdo/src/main/docs/root-columns.md) and
[Locking](../../../../tentackle-persistence/src/main/docs/locking.md) for what each one is for). Both
tables list each attribute's name, column, Java type, **SQL type** (e.g. `VARCHAR(128)`, suffixed with
`NOT NULL` for non-nullable columns and the `DEFAULT` clause if the attribute declares one, exactly as
in the backend's DDL) and comment.

Below the attribute tables, an **Indexes** section lists the entity's additional, model-declared
indexes (an entity's `## indexes` section — not the implicit primary key) as the actual,
backend-specific `CREATE INDEX`/`CREATE UNIQUE INDEX` statements, the same statements `create` would
emit for the same model.

The entity page's meta table shows the **Table** name relative to its schema (the schema itself, if
any, is shown in the separate **Schema** row right below, so it isn't repeated). If `mapSchemas` is set,
the table name shown is the effective, flattened name actually used at runtime (see `mapSchemas` under
[Model selection](#model-selection) above) — and since a mapped entity no longer has a separate schema,
the **Schema** row is omitted for it.

```bash
mvn tentackle-sql:document -Dtentackle.backendNames=h2
mvn tentackle-sql:document -Dtentackle.backendNames=h2 -Dtentackle.docFormat=markdown
```

Never connects to a database — it only needs a `Backend` for its SQL-to-type mapping, not a connection —
but because that mapping can differ between backends, at least one must be selected, same as `create`
(see [Backend selection](#backend-selection) above). Usually that is `backendNames`, but backends
configured via `backendProperties` or `backends` for the other goals are documented as well. One
self-contained page tree is generated per backend. There is no default — like `create`, nothing is
generated if no backend is configured. Parameters (beyond the shared ones listed above):
- `format` (`tentackle.docFormat`): the output format, `html` (default) or `markdown` (alias `md`),
  case-insensitive. See [Markdown output](#markdown-output) below.
- `docDir` (`tentackle.docDir`): directory to create the pages in, for both formats. Defaults to
  `${project.build.directory}/model-doc`.
- `title` (`tentackle.htmlTitle`): the heading shown on the index page, for both formats. Defaults to
  the maven project's name.
- `loadModelFromClassPath` (`tentackle.loadModelFromClassPath`): also render entities from the model
  found on the classpath (e.g. a dependency's own model), so entities referenced from a dependency
  aren't dead links. Unlike `migrate`, `document` loads the local model files as well.
- `cssFile` (`tentackle.cssFile`): a project-specific stylesheet, copied verbatim to `style.css` in
  every backend's page tree. HTML only — ignored (with a warning) for `markdown`.

#### Markdown output

With `format=markdown`, the same content is written as `<Entity>.md` pages plus an `index.md`, for
dropping the model documentation into a Markdown-based doc tree (MkDocs, Bitbucket/GitHub, an IDE's
Markdown preview). Navigation is the same as for HTML: every entity mentioned — in the relationship
sections, the composite trees, the inheritance section and the **Extends** row — is a relative link to
that entity's `.md` page, every entity page starts with a link back to `index.md`, and the index links
every entity page.

The pages use GitHub-flavored Markdown: pipe tables for the meta and attribute tables, a fenced
SQL code block for the indexes, and 4-space indentation for nested lists, which both CommonMark and
Python-Markdown (MkDocs) render as nested. Model comments are escaped, so Markdown or HTML syntax in a
comment shows up literally. No stylesheets are generated: the look is up to the Markdown renderer.

#### Styling the generated pages

Applies to the `html` format only. Each page loads two stylesheets: `base.css`, always generated, holds the structural rules (tables,
lists, spacing) and has no reason to be touched; `style.css` holds the theme (colors, fonts) and is
where a project's own look belongs. `base.css`'s colors are `var(--tentackle-doc-*, <neutral default>)`
custom properties, so `style.css` only needs to redefine the ones it cares about — or ignore the
variables and override selectors outright, since `style.css` is loaded after `base.css` and wins the
cascade either way.

Without a `cssFile`, the generated `style.css` mimics **tentackle.org**'s own brand: dark blue
headings and links, the signature orange-framed `h2`/`h3` (a 1px top/bottom rule in the same color as
the heading text and link hover), a dark-blue-banded attribute table header, Roboto, and a
`prefers-color-scheme: dark` variant using the site's own dark-mode palette (lighter orange, muted
blue-gray links). It is the same palette applied to the docs site
(`src/mkdocs/theme/stylesheets/extra.css`) and the generated Maven site
(`src/site/resources/css/site.css`), so model documentation generated by this goal looks at home next
to the rest of the project's generated docs. The variables it sets —
`--tentackle-doc-font`, `--tentackle-doc-text-color`, `--tentackle-doc-background-color`,
`--tentackle-doc-border-color`, `--tentackle-doc-heading-color`, `--tentackle-doc-accent-color`,
`--tentackle-doc-link-color`, `--tentackle-doc-comment-color`,
`--tentackle-doc-table-header-background-color`, `--tentackle-doc-table-header-text-color` — are a
ready-made starting point for a `cssFile`: copy the generated `style.css` and change what you want,
including the `@media (prefers-color-scheme: dark)` block.

### The `reveng` Goal

Every other goal on this page turns the Tentackle model *into* a database. `reveng` is the one goal
that goes the other way: it reverse-engineers tables of an **existing** database into
[model source](../../../../tentackle-model/src/main/docs/model-definition.md) text, for introducing
Tentackle into a project whose schema already exists. It does not touch this plugin's own `modelDir`/
`filesets` or generate any Java code itself; it is a small, standalone first step that produces the
files `tentackle-wizard:pdo -DbatchDir=…` then consumes:

```
mvn tentackle-sql:reveng -Dtentackle.reveng.url=jdbc:postgresql://localhost/legacydb \
                          -Dtentackle.reveng.user=app -Dtentackle.reveng.password=secret \
                          -Dtentackle.reveng.tables=CUSTOMER,ORDER_ITEM
mvn tentackle-wizard:pdo -DbatchDir=target/reveng-model
```

For each requested table it reads columns, indexes and foreign keys via JDBC metadata
(`org.tentackle.sql.metadata` — the same introspection layer `migrate`/`validate` use to compare a
database against the model) and writes one model-source file into `outputDir`
(`target/reveng-model` by default). Parameters (all `tentackle.reveng.*` properties):

- `url`, `user`, `password` (required except `password`): the JDBC connection to the *existing*
  database — independent of this plugin's own `backends`/`backendProperties` configuration, and
  typically only used once, for the reverse-engineering run itself.
- `schemas`: optional comma-separated list of schema names to restrict introspection to.
- `tables` (required): comma-separated list of table names to reverse-engineer.
- `outputDir` (default `${project.build.directory}/reveng-model`): where the generated model source
  files are written, one `<EntityName>.map` per table.
- `startClassId` (default `1`): the class id assigned to the first table (in the order of `tables`);
  subsequent tables get consecutive ids. Batch-mode model source always needs a concrete, non-zero
  class id, so — exactly as when hand-writing batch model files — choosing a range that does not
  collide with the target project's already-assigned class ids is the caller's responsibility.
- `integrity` (default `related`): the `integrity :=` value applied to every generated entity. The
  default assumes an application-checked relation with a database foreign key, since a physical
  foreign key was, by definition, already found in the database for any relation this goal emits.
- `stereotype`: optional stereotype (without the `#`) written into every generated entity, so that
  `tentackle-wizard:pdo`'s batch mode can pick the matching `PdoProfile` when more than one is
  configured.
- `entityOptions`: additional entity option flags written verbatim into every generated entity's
  global options line, comma-separated, e.g. `remote, tracked`.
- `overwrite` (default `false`): whether to overwrite files already present in `outputDir`.

**What gets inferred, and what does not.** A foreign key becomes a plain, non-composite object
relation using `integrity`; whether it should really be a `component`/`composite` relation, use
`delete = cascade`, or an eager `select` strategy cannot be inferred from schema metadata alone —
these are aggregate-design decisions the DDL does not encode, so the generated `.map` file is a
starting point to hand-edit before running `pdo`, not a finished model. A foreign key referencing a
table that is not part of the same `reveng` run is left as a plain attribute (with an explanatory
comment) instead of a relation, since `pdo`'s batch mode loads every file in `outputDir` together and
cannot resolve a relation to an entity that isn't among them — reverse-engineer the referenced table
in the same run (or add the relation by hand afterward) if you need it. A table without a literal
`id` column does not fit Tentackle's synthetic-identity object model; it is still reverse-engineered,
but declared `[nopkey]` and will not behave like a normal identity-bearing PDO. Column `NOT NULL`
constraints are represented by choosing a Java primitive over its wrapper type where one exists (the
model has no other way to express column nullability); for types without a primitive form (`String`,
dates, `BigDecimal`, …) a `NOT NULL` column instead gets a `@NotNull` validation, since the database
constraint itself cannot be reproduced that way.

### The Skills

`src/skills/` in this module holds three ready-made agent skills: `tentackle-sql-migrator` for
`migrate`/`validate` — generating the migration, what the migrator matches by itself, when a hint is
needed, and reading the script before it runs — `tentackle-sql-runner` for `run`, i.e. when to
prefer plain SQL over the domain-model tools and what to watch out for — and `tentackle-sql-reveng`
for `reveng`, i.e. what a foreign key becomes, what to check in the generated `.map` files before
handing them to `tentackle-wizard:pdo`, and the class-id range that goal knows nothing about. There is
deliberately none for `create`: it emits the DDL of the whole schema and belongs to bootstrapping an
empty database, not to changing an existing one. They are templates; copy them into your project:

```bash
mkdir -p .claude/skills
cp -r path/to/tentackle-sql-maven-plugin/src/skills/* .claude/skills/
```

See [AI Agent Tooling Support](../../../../src/main/docs/ai-agents.md) for how it fits together with the
model MCP server and the headless wizard goals.

### How It Fits Into the Build

For a typical Tentackle application, the database tooling builds on the output of the wurbelizer:

1. The wurbelizer extracts the entity model from the PDO interfaces and writes it to
   `target/wurbel/model`.
2. `tentackle-sql:create` turns that model into the initial schema script — run once to bootstrap a
   database, or wired into a profile that initializes the test database.
3. As the model evolves, `tentackle-sql:migrate` (guided by migration hints) produces the incremental
   scripts that bring existing databases forward, and `tentackle-sql:validate` guards that databases
   stay in sync.

For a **brownfield** project — a database that exists before Tentackle is introduced — there is a step
0: `tentackle-sql:reveng` reads that existing database and writes the model source that
`tentackle-wizard:pdo` turns into the PDO interfaces the wurbelizer then extracts from in step 1.
